# Quake-mod launch failure after native graphical mux changes

Date: 2026-07-11  
Reporter: quake-mod workspace  
Status: confirmed RCA; no fix applied  
Severity: high for graphical applications launched outside a mux-owned pane scope

## Executive summary

The quake-mod FTEQW runtime is not failing during engine, asset, or OpenGL
initialization. The live EngineOS compositor deliberately closes its Wayland
surface because the FTEQW process was launched outside a transient user scope
registered to a native mux pane.

The quake-mod launcher currently executes `fteqw-glsdl2` directly. Native mux
mode, enabled by default on 2026-07-11, now treats the registered systemd user
scope as the authoritative surface-to-pane identity and fails closed when a
client cannot be resolved to one. These two contracts are incompatible.

This is not specific to FTEQW. The shell log contains the same rejection for
Cube, Foot, Falkon, and other graphical processes launched without the native
pane registration path.

There is also a separate test-isolation defect: a headless `eos-test` run
launched the real `engineos-quake.service` and left the user systemd manager
with `WAYLAND_DISPLAY=wayland-1`, while the live compositor uses `wayland-0`.
That defect can break the standalone QuakeSpasm service path, but it is not the
cause of the confirmed live FTEQW rejection.

## User-visible symptom

Launching the quake-mod RPG runtime creates a window briefly or appears to do
nothing. FTEQW reports that its display is disconnected and exits. The game
does not reach a visible, interactive state in the live EngineOS shell.

## Confirmed live failure

At approximately 15:32 local time, the live shell recorded:

```text
view initial configure id=3 role=mux-presentation title=(untitled) app_id=fteqw-glsdl2
view fullscreen request role=mux-presentation fullscreen=true title=FTE QW app_id=fteqw-glsdl2
native presentation rejected pid=367317 surface=3 reason=process is not in a registered user scope title=Quake RPG Runtime: disconnected app_id=fteqw-glsdl2
view unmapped role=mux-presentation id=3 title=Quake RPG Runtime: disconnected app_id=fteqw-glsdl2
view destroyed role=mux-presentation id=3 title=(untitled) app_id=(unknown)
```

The shell's rejection path disables the scene node, marks the view unmapped,
and sends an XDG toplevel close event to the client. The client is therefore
being closed by policy; it is not crashing independently.

Relevant implementation locations:

- `shell/src/engineos-shell.c`, native presentation rejection path near line
  7893.
- `packages/engineos-mux/engine-pane.c`, PID-to-pane resolution near line 346.
- `packages/engineos-mux/engine-pane.c`, scope membership check using
  `sd_pid_get_user_unit()`.

The mux returns `process is not in a registered user scope` when the client PID
does not belong to a systemd user unit registered by `launch-pane-app`.

## Launch-path mismatch

The quake-mod canonical launcher is:

```text
/home/dev/quake-mod/tools/run-rpg.sh
  -> /home/dev/quake-mod/tools/run-rpg-fteqw.sh
  -> /home/dev/quake-mod/engine/fteqw/engine/release/fteqw-glsdl2
```

`run-rpg-fteqw.sh` directly `exec`s the FTEQW client. It does not invoke
`engine-mux launch-pane-app`, create a mux-owned transient scope, or provide an
authoritative pane target.

Tang-OS already has the intended native launch mechanism in
`tools/scripts/app.sh`:

```text
eos-app pane launch --game -- COMMAND
  -> engine-mux launch-pane-app -g -t PANE -- COMMAND
```

The native Quake branch in `eos-app launch quake` only selects that route when
both `TMUX` and `TMUX_PANE` are inherited. A shell launchpad action does not
reliably inherit a terminal pane identity, and a direct quake-mod launcher
bypasses `eos-app` completely.

Native graphical mux became the default in commit `91af89c` (`Enable native
graphical mux by default`). The direct FTEQW launcher predates that system-wide
acceptance rule.

## Evidence that the engine and graphics stack are not the root cause

- The FTEQW executable exists and reaches Wayland surface creation.
- The client successfully issues a fullscreen request.
- The shell identifies its `app_id` as `fteqw-glsdl2`.
- Quake assets are present at `/home/EngineOS/assets/quake/id1`.
- Asset manifest validation reported zero failures.
- The live shell renderer is AMD/radeonsi on an RX 5600 XT with no current
  output frame failures.
- No FTEQW or Quake core dump corresponds to the live rejection.
- The compositor logs an explicit policy rejection before unmapping the view.

An FTEQW warning about initial `0x0` effective window geometry is a real
compatibility issue and should be corrected, but it is not what closes the
current client: the explicit native-scope rejection immediately follows it.

## Separate headless-test finding

The QuakeSpasm journal record at 13:54 local time was generated by an
`eos-test` headless smoke run, not by the live FTEQW attempt.

The event log identifies `eos-test` at `2026-07-11T16:54:13Z`. The temporary
headless compositor selected `wayland-1`, bootstrapped all launchpad apps, and
started the real `engineos-quake.service`. QuakeSpasm successfully initialized
video, OpenGL, assets, and audio. The headless compositor then reached its
expected one-second smoke timer and shut down, causing SDL to report:

```text
ERROR: Wayland display connection closed by server (fatal)
```

That shutdown is expected for the smoke compositor, but starting real user
services from the test is not isolated. The user systemd manager currently
advertises:

```text
WAYLAND_DISPLAY=wayland-1
```

The live compositor socket is:

```text
/run/user/1000/wayland-0
```

Only `wayland-0` currently exists. A later standalone service launch may
therefore fail before mapping because it inherits a stale display name.

## Root cause

Primary root cause:

> Native mux changed graphical client admission from app-ID/launch ownership
> to a fail-closed, systemd-scope-based pane identity, but the quake-mod FTEQW
> launcher and some shell launchpad paths were not migrated to create and
> register that scope.

Contributing architectural gap:

> Pane selection is inferred from inherited `TMUX`/`TMUX_PANE` variables.
> Shell-owned launchpad actions need an authoritative pane or output target
> even when no terminal process environment is involved.

Separate contributing defect:

> Headless integration tests can mutate the persistent user-manager graphical
> environment and start real graphical services against temporary compositor
> sockets.

## Recommended fix

Do not weaken or bypass the compositor's scope validation. It is an important
ownership boundary and weakening it would hide the broken launch contract.

Implement one canonical native graphical-game launch path:

1. Add the quake-mod FTEQW runtime as an explicit EngineOS game provider or
   command accepted by the native app layer.
2. Route every interactive FTEQW launch through
   `engine-mux launch-pane-app -g`.
3. Make the shell or mux select and pass the authoritative target pane/output;
   do not require launchpad children to guess it from `TMUX_PANE`.
4. Keep the leaf FTEQW/SDL PID inside the registered transient scope and verify
   it through `sd_pid_get_user_unit()`.
5. In native mode, retire the standalone graphical-service route where it
   conflicts with mux ownership, or redesign it so the mux-owned transient
   scope remains authoritative.
6. Return a clear failed app state such as `scope-rejected` when admission
   fails instead of leaving the app at `launch-requested`.

For test isolation:

1. Headless tests must not restart real user graphical services.
2. Use foreground clients attached only to the temporary compositor or a
   fully isolated/faked service manager.
3. Do not persist a temporary `WAYLAND_DISPLAY` with
   `systemctl --user import-environment`.
4. Verify after the test that the user-manager display environment is
   unchanged.

## Acceptance criteria

The fix is complete only when all of the following are proven on the live
native-mux shell:

- Launching the quake-mod RPG from a terminal pane maps FTEQW into that pane.
- Launching it from the shell launchpad maps it into the shell-selected game
  pane without relying on inherited `TMUX_PANE`.
- The FTEQW PID resolves to exactly one registered transient user scope.
- The shell logs `native presentation mapped`, not `native presentation
  rejected`.
- Fullscreen/game presentation and input capture work, and emergency release
  still returns input to the shell.
- Exiting or relaunching FTEQW cleans up its scope without leaving stale pane
  ownership.
- An intentionally unregistered Wayland client remains rejected.
- A headless smoke run neither starts the real Quake service nor changes the
  user manager's `WAYLAND_DISPLAY`.
- A subsequent live Quake/FTEQW launch still connects to the live compositor.

## Suggested regression coverage

Prefer contract/integration tests over assertions on incidental log wording:

1. Registered game scope: start an SDL/Wayland child through
   `launch-pane-app -g`, map it, and prove its PID belongs to the pane scope.
2. Launchpad game: request a game from a shell-owned launch action with no
   terminal environment and prove a target pane was selected explicitly.
3. Negative admission: launch an unregistered client and prove it is rejected.
4. Child process: use a wrapper that `exec`s or spawns the real SDL client and
   prove the leaf PID is recognized.
5. Test isolation: record the user-manager environment before and after a
   headless smoke and require exact preservation of graphical display fields.

## Read-only investigation scope

The RCA was produced from status, source, process, package, shell-log, journal,
and coredump inspection. No services were restarted, no application was
launched for reproduction, and no engine, shell, package, or runtime behavior
was changed during the investigation.
